# Наполнение каталога

## Что уже работает

Самостоятельная страница `/Reestr3/catalog/`, поиск, уточняющие фильтры, сортировка, список и карточки, пагинация, паспорта, ссылки на подборку и конкретную запись, связи наследия и предметов, фотографии с увеличением и CSV всей найденной подборки. URL и обновление работают на статическом GitHub Pages: сборка содержит настоящий `catalog/index.html`, а параметры хранятся в query string, без серверных rewrite.

Это публичная часть каталога, не серверная редакторская система. Браузер не записывает музейные данные в localStorage и не имитирует общее хранилище. Изменения содержания вносятся в источник данных и входят в следующую сборку. Для многопользовательской админки потребуются отдельные сервер, БД, роли и решение о хостинге.

## Где менять сведения

- `src/catalog-data.mjs` - описания наследия, реальные предметные серии и метаданные медиа.
- `src/catalog.mjs` - народы, категории, подкатегории, сохранность, правила фильтров и проверки.
- `public/assets/objects/` - обработанные JPEG. В коде путь начинается с `assets/objects/`, без `/Reestr3/`: базовый путь подставляет приложение.

Фотографии копируются, а не перемещаются из авторских рабочих папок. Оригиналы, PNG-мастера и исходные RAW остаются на месте. Один физический предмет занимает одну карточку, фотографии разных сторон находятся внутри `media`. Архивное изображение не добавляется в его галерею автоматически.

## Поля записи

`id` - постоянный уникальный идентификатор для URL. Не менять при редактуре названия. `code` - уникальный внутренний код каталога, не номер государственного реестра. `type`: `heritage` или `museum`. `people`: `shor` или `teleut`. `category` и `subcategory` - ключи существующего классификатора. `place` у традиции обозначает территорию, у фотографируемого предмета - место съёмки; последнее не доказывает происхождение предмета.

`title`, `summary`, `description` (массив абзацев) заполняются редакционным текстом. `status` отражает документированную сохранность: `preserved`, `partial`, `transformed`, `lost`, `unknown`. `unknown` не заменять догадкой. `editorialStatus`: `draft` до научной редакции, `reviewed` только после проверки. `transmission` описывает передачу традиции при наличии сведений.

Для предмета: `museum`, `inventoryNumber`, `materials`, `dimensions`, `dating`. Неизвестные сведения остаются `null`, интерфейс показывает понятную подпись. Название учреждения из рабочей подписи к съёмке ещё не заменяет сверку фондовой карточки.

`related` - массив ID из другого раздела. Связь должна быть двусторонней: оба объекта перечисляют ID друг друга. Связь предмета с тематическим контекстом не устанавливает его принадлежность конкретному обряду; в текущих текстах это ограничение отмечено.

## Фото, видео и источники

Медиа: `{ type: 'photo', src: 'assets/objects/имя.jpg', caption: 'Ракурс', credit: 'Автор и сведения об обработке' }`. Для локального видео `type: 'video'`, файл в `media/` или `assets/`. Внешние видеоплееры и трекеры автоматически не подключаются. Каждый файл должен существовать в `public/`.

Источники: `{ title: 'Название публикации', url: 'https://...', note: 'При необходимости' }`. Только проверенные HTTPS-адреса без логина/пароля. HTML в описаниях не исполняется. Для фото и видео необходимо согласовать происхождение и режим использования до публичной публикации.

Сейчас добавлены две обработанные серии бубнов (4 и 3 ракурса) из ранее подготовленной папки. Наименования и этническая атрибуция рабочие; музейные номера не придуманы. Тексты традиций временные по прямому разрешению владельца. Последующая научная редактура меняет данные, а не устройство страницы.

## Проверка перед обновлением

`npm run catalog:validate` проверяет ID, коды, обязательные поля, классификаторы, двусторонние связи, безопасные адреса медиа и наличие файлов. `npm test` проверяет поведение фильтров, URL, пагинации, сортировки и CSV. `npm run build` автоматически запускает валидатор и формирует обе страницы.

`npm run preview -- --host 127.0.0.1 --port 4174` позволяет проверить готовую сборку. После публикации проверять прямой URL каталога и открытие конкретного паспорта с обновлением страницы. Push в `main` запускает публикацию GitHub Pages, поэтому выполнять его только по явной команде владельца.
